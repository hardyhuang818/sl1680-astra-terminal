一 · 远程访问

拓扑

PC(192.168.5.166) → 家OpenWrt(192.168.5.1) → wg0(10.0.0.1↔10.0.0.2) → BE3600(192.168.8.1) → SL1680(192.168.8.186)

连接方法（必须 native ssh）

ssh -o StrictHostKeyChecking=no -o UserKnownHostsFile=NUL \
    -J root@192.168.5.1 root@192.168.8.186 "<命令>"
  • paramiko 连不上跳板：IncompatiblePeer: no acceptable ciphers
  • 密码用 SSH_ASKPASS 喂（跳板 / 板子两个密码，脚本按提示里的 IP 分辨）
  • 辅助脚本：wgrun.ps1(跑命令) wgsh.ps1(跑脚本) wgput.ps1(传文件)
三个坑
  1. PC 默认网关是 Surge(192.168.5.242) 不是 WG 路由器 → Test-NetConnection 192.168.8.186 -Port 22 会假阳性返回 True（Surge 先接受 TCP），真连才报 Error reading SSH protocol banner。别信这个端口测试。
  2. 必须走 PowerShell 不能用 Git Bash —— 后者把 /tmp 改写成 Windows 路径
  3. 上传文件会被注入 3 字节 UTF-8 BOM（.NET StandardInput）：文本没事，二进制直接废（Exec format error）。判据：板上大小 = 本地 +3，传完剥掉即可

二 · C920 麦克风崩溃循环

现象：astra-voice NRestarts=31，报 Unable to set hw params for CAPTURE: Protocol error

✅ 已验证的现象：dmesg 里 1-1.3 上 device number 6→7→8→9 连环 new，即该总线上有设备在反复重枚举；C920 音频接口打不开、服务反复重启；换一个 USB 口后问题消失，录音峰值 3414/1806/939 全部正常，NRestarts 归 0。

⚠️ 高概率推断的根因：重枚举的是 DisplayLink dock，其总线抖动打断了 USB 等时传输（isochronous），导致声卡开不了。

推断依据是时间相关性 + 换口即好，但没有直接证据证明是 isochronous 被打断（而不是带宽被吃满、供电跌落、或 hub 本身的问题）。要坐实需要：lsusb -t 确认换口前后确实跨了不同 root hub；重现时看 /sys/kernel/debug/usb/devices 的等时带宽分配；或故障态下 usbmon 抓包看等时传输错误码。这些当时都没做 —— 问题已经好了，没有再制造故障去验证。

教训：USB 声卡报 Protocol error，先怀疑同总线上有设备在抖，换口最快。但"换口有效"只能证明和总线有关，不能证明具体是哪一层出的问题。

三 · DL7400 中英对照实时字幕

astra_voice ─写─> /tmp/astra_status.txt (中文, 原封不动) ↓ 轮询200ms astra_translate.py ─DeepSeek翻译+LRU缓存─> /tmp/astra_status_en.txt ↓ (HEARD_EN/HEARD_SRC/REPLY_EN/REPLY_SRC) dl_face ─读两个文件─> 屏幕双语

为什么分两个文件

astra_voice 每次状态变化整文件覆盖写，追加进去必被冲掉；分开还让翻译延迟完全不拖累语音回复。

对抗性审查逼出来的关键设计

  1. 关联键 HEARD_SRC/REPLY_SRC —— 两文件各自更新有几百 ms 错位窗口，dl_face 必须比对一致才显示英文，绝不把上一句英文配到这一句下面
  2. REPLY 是逐句流式写的（每合成一句就换成更长前缀）→ 首次 0 去抖立刻翻（speaking 窗口只有 2-4 秒），之后等停止增长 1.2s 再翻最终版
  3. 翻译请求 Semaphore(1) 串行 —— 避免和语音主链路抢 key 并发被限流
  4. ExecStopPost=rm -f 译文文件 —— 否则进程停了残留旧英文一直错配（最难发现的故障）
  5. 字幕字号保持 0.05 不缩 —— textoverlay 按文本块中心定位，1 行变 2 行只上下各扩半行，2880×1800 完全放得下

交叉编译

wsl -d Ubuntu-22.04 -- bash "/mnt/d/Claude code/Case6_Astra/astra-xiaozhi/build-dlface-wsl.sh"

必须 PowerShell 调。备份：仓库 dl_face.c.orig、板上 /usr/bin/dl_face.bak

四 · 联网层（杜绝幻觉）

🚨 血泪结论：智谱 chat 接口的 web_search 工具不工作 
glm-4-plus 「联网」 → "15到25℃"    搜索结果 0 条   prompt_tokens=21
glm-4-air  「联网」 → "18到28℃"    搜索结果 0 条   prompt_tokens=21
真实气温            → 28~36℃
两个模型互相矛盾且都是错的——它们在编造。

✅ 已验证：两个模型给出互相矛盾的气温，且都和真实值差得离谱（15~25 / 18~28 vs 实际 28~36）。不管内部发生了什么，这个接口不能用来回答实时问题 —— 这一条是直接测出来的，不依赖任何推断。

⚠️ 高概率推断：它们在编造，因为压根没搜。判据是 prompt_tokens=21 —— 真联网了搜索结果会注入上下文，token 数应是几百上千，21 大致就是原始问题本身的长度。

这个判据单独一条并不足以定案：也可能搜了但结果不计入 prompt_tokens，或搜索在服务端另行统计。同时看到的旁证是响应里 search_result 为空（0 条），两条合起来才指向"没搜"。真要坐实，得让智谱确认该接口在本账号/本模型下 web_search 是否真正启用。

不过这不影响决策：无论根因是"没搜"还是"搜了没用上"，结论都一样 —— 改用独立搜索 API。

✅ 正确做法：调独立搜索 API

POST https://open.bigmodel.cn/api/paas/v4/web_search
{"search_engine":"search_std","search_query":"...","count":5,"search_recency_filter":"oneDay"}
→ 2.3 秒返回 10 条真实网页内容
  • search_std(¥0.01/次) 比 search_pro(¥0.03/次) 更适合天气：前者给气象站数据，后者返回新闻稿
  • 模型免费 ≠ 搜索免费，搜索按次计费

实现：关键词命中 → 拿真实结果 → 塞给 DeepSeek 配 GROUND_PROMPT（"只根据这些资料回答，找不到就说不知道，绝对不许编造数字"）。实测实时问题 5 秒、普通问题 2 秒。

正确的 CPU 测量方法（别用 top 单次采样）

def read():
    v=[int(x) for x in open("/proc/stat").readline().split()[1:]]
    return sum(v), v[3]+v[4]     # total, idle+iowait
t0,i0=read(); time.sleep(10); t1,i1=read()
print(100.0*((t1-t0)-(i1-i0))/(t1-t0))

七 · 双屏分工

屏0 (AOC Q2790R3 2560x1440) 屏1 (2880x1800) 对话界面：表情 + 中英字幕 默认表情脸，说"打开监控"→ C920 实时画面 （永远在这块）
  • 「打开监控」→ 屏1 切摄像头 + 自动停 vision-wake，回复"已在第二块屏打开监控画面，视觉唤醒先暂停了"
  • 「关闭监控」/「换回表情脸」→ 屏1 变回表情 + 自动恢复 vision-wake
两个关键限制
  1. C920 是独占设备 —— camera 模式和 vision-wake 只能二选一
  2. 摄像头被占时 vision-wake 会静默空转（日志连错误都不报）—— 排查要看"有没有帧文件/检测心跳"，不能只看 systemctl is-active

排查要点

  • dl_edid 必须先 systemctl stop dl-face（dlsdk 是 userspace libusb 单进程独占），否则报"找不到设备"
  • dl_face 只在启动那一刻枚举显示器 → 已加 ExecStartPre=/bin/sleep 20，冷启动实测靠它才认到 2 块
  • 视频节点号每次开机会变（C920 这次 video3、上次 video8）→ 必须用 by-id
  • UVC 相机有两个节点：video-index0=采集、index1=元数据（后者不能抓帧）

八 · 环境噪音与误触发

6 段采样: 600 / 632 / 646 / 713 / 575 / 592
底噪 RMS: 575~713, 平均 626

原门槛 --min-rms 300 是底噪的一半 → 持续误触发，助手不停把空调声当说话、白烧 API。已改 300 → 1150、--min-dur 0.4 → 0.6。静置 40 秒零触发。

根本矛盾：用户说话 RMS 约 470~1170，和底噪 575~713 重叠——单靠能量门槛无法完美区分。代价：必须靠近麦克风（30cm 内）说。根治方案是 KWS 唤醒词。
