核心原則：不 fork 官方 SDK。 上游鎖定在 tag，我們的全部修改都放在兩個自有 Yocto 層裡 （核心改動以 bbappend + patch 形式套在官方 linux-syna 上）。官方升級時只需換 tag 重新驗證。

1. 主機需求（實測配置）

項目 本機實際 最低建議
系統 Ubuntu 22.04.5 LTS（WSL2） Ubuntu 20.04/22.04，實體機或 WSL2 皆可
CPU 24 核 ≥8 核（核心越多全量建置越快）
記憶體 47 GB ≥16 GB（連結 chromium/qt 時吃記憶體）
磁碟 1 TB（已用 357 GB，其中 tmp/ 佔 159 GB） ≥500 GB 可用空間，SSD
Python 3.10.12 ≥3.8
git 2.34.1 ≥2.28

WSL2 使用者注意：SDK 務必放在 WSL 原生檔案系統（/home/...），不要放 /mnt/c —— 跨檔案系統 IO 會讓建置慢一個數量級。本機的 WSL 虛擬磁碟另外掛了 1TB（/dev/sdd）。

3. 建置指令全集

每個新終端機都要先進環境（bitbake 只在 source 之後可用）：

cd ~/sdk && source poky/oe-init-build-env build-sl1680

3.1 全量映像檔（首次約 3~6 小時，視機器而定）

bitbake astra-media

產出物在 tmp/deploy/images/sl1680/：

檔案 用途
SYNAIMG/ 完整燒錄包（約 2.5GB），搭配官方 USB 燒錄工具
astra-media-sl1680.rootfs.ext4 rootfs 單獨映像檔
linux_bootimgs.subimg boot 包（kernel + DTB + initramfs），可單獨 dd
Image-sl1680.bin / *.dtb 裸 kernel / 裝置樹

3.2 核心快速疊代（日常最常用，全程約 75 秒）

改了 dolphin-rdk.dts 或核心原始碼之後：

bitbake linux-syna -C compile        # 大寫 C：強制從 compile 重跑（含 dts 重編）
bitbake linux-syna -c deploy -f      # 強制重新部署產出物

⚠️ 直接改的是 tmp/work-shared/sl1680/kernel-source/ 下的原始碼 —— 這個目錄是易失的，cleanall 就沒了。改完必須回灌成 patch 放進 meta-dlsdk/recipes-kernel/linux/files/（如何正確產生 patch 見 §5.6）。

改完後必須做位元組級 DTB 驗證（建置成功 ≠ 改動生效）：

python3 - <<'EOF'
b = open("/home/astra/sdk/build-sl1680/tmp/deploy/images/sl1680/dolphin-rdk.dtb","rb").read()
print("我的節點在嗎:", b"synaptics,tcm-i2c" in b)
EOF

3.3 單一套件建置（改了某個 recipe 之後）

bitbake astra-voice                  # 語音主程式
bitbake sherpa-onnx                  # 本地 ASR/TTS 執行環境
bitbake dl-face                      # DL7400 對話介面
bitbake synaptics-tcm2               # 觸控驅動核心模組(meta-tcm2-touch)

3.4 清理（由輕到重）

bitbake <recipe> -c clean            # 清 work 目錄，保留 sstate
bitbake <recipe> -c cleansstate      # 連 sstate 一起清（強制真重編）
bitbake <recipe> -c cleanall         # 再連 downloads 一起清（會重新下載！慎用）

驗證「patch 能否從零套用」用 cleansstate + 重編即可，不要動不動 cleanall。

3.5 排查與檢查

bitbake <recipe> -e | grep ^SRC_URI=          # 看變數展開後的實際值
bitbake <recipe> -c devshell                  # 進 recipe 的建置環境 shell
bitbake-layers show-recipes "*tcm*"           # recipe 在哪個層
bitbake-layers show-appends linux-syna        # 誰 append 了它
oe-pkgdata-util find-path "*/astra_voice"     # 檔案屬於哪個套件

建置日誌位置：tmp/work/<arch>/<recipe>/<ver>/temp/log.do_<task>

4. 燒錄

4.1 全量燒錄（USB 工具，第一次/大版本用）

Windows 側用官方 usb-tool-astra-update（板子進 USB 燒錄模式）， 把 SYNAIMG/ 整個目錄餵給它。約 2.5GB，10 分鐘內。

4.2 只刷 boot（核心/DTS 疊代用，30 秒）

板子運作中直接 dd（A/B 雙槽都刷）+ sha256 回讀校驗：

scp tmp/deploy/images/sl1680/linux_bootimgs.subimg root@192.168.5.126:/tmp/
ssh root@192.168.5.126 'sh -s' <<'EOF'
IMG=/tmp/linux_bootimgs.subimg
SZ=$(wc -c < $IMG)
dd if=$IMG of=/dev/mmcblk0p8 bs=1M 2>/dev/null
dd if=$IMG of=/dev/mmcblk0p9 bs=1M 2>/dev/null
sync
python3 -c "
import hashlib
exp = hashlib.sha256(open('$IMG','rb').read()).hexdigest()
for d in ('/dev/mmcblk0p8','/dev/mmcblk0p9'):
    got = hashlib.sha256(open(d,'rb').read($SZ)).hexdigest()
    print(d, 'OK' if got==exp else 'MISMATCH!')
"
EOF

然後斷電重上（見 §5.1，這塊板軟重啟不可靠）。

4.3 燒完映像檔後還缺兩樣

缺什麼 怎麼補
約 2GB 語音模型（不進映像檔） 另外灌到板子 /home/voice/，清單見 meta-dlsdk/recipes-ai/astra-voice/files/README_models.md
DLSDK 二進位檔（DisplayLink NDA） 建置前放入 meta-dlsdk/recipes-graphics/dlsdk/files/，清單+sha256 見同目錄 BINARIES_MANIFEST.txt；不用 DL7400 就在 local.conf 設 ASTRA_TERMINAL_PACKAGES = ""

5. 踩過的坑（每條都真踩過，按血淚值排序）

5.1 這塊板軟重啟不可靠

reboot -f、systemctl reboot -ff、sysrq 全部無效。每次刷完 boot 都按「需要人工斷電重上」來安排， 改動盡量攢成一次重啟。

5.2 bbappend 檔名的版本萬用字元規則（兩邊坑正好相反）

  • linux-syna recipe 帶版本號（6.12.62）→ append 必須寫 linux-syna_%.bbappend（帶 _%）
  • tzdata recipe 不帶版本號 → append 必須寫 tzdata.bbappend（不帶 _%） 寫反的症狀都是 No recipes available for ...，bitbake 不會告訴你是檔名的問題。

5.3 cmake FetchContent 被 Yocto 硬關（症狀像斷網）

cmake.bbclass 預設 FETCHCONTENT_FULLY_DISCONNECTED=ON，第三方套件在 do_configure 階段 下載失敗，錯誤看起來像網路問題——其實根本沒連網。解法：全部第三方套件寫進 SRC_URI （帶 sha256）+ do_configure:prepend 拷到原始碼樹命中 possible_file_locations。 參照 meta-dlsdk/recipes-ai/sherpa-onnx/sherpa-onnx_1.13.4.bb（14 個套件的完整做法）。

5.4 無 SOVERSION 的 .so 會被打進 -dev 套件

建置全綠、套件也出了，燒到板子上就是沒有那個 .so ——它被分進了 -dev 套件。 症狀離建置極遠，極難回溯。解法見 sherpa-onnx recipe 裡的 SOLIBS/FILES 處理。

5.5 映像檔整合四坑（建置成功 ≠ 功能完整）

① 兩個套件裝同一個檔案 → do_rootfs 衝突；② 兩個服務搶同一裝置（DLSDK 單行程獨佔）； ③ 套件裝進去了但服務沒 enable（SYSTEMD_AUTO_ENABLE 只在 recipe 裡生效， SYSTEMD_AUTO_ENABLE:pn-X 寫在 conf 裡不生效）；④ 驗收必須用 debugfs 直讀產出的 ext4， 別信建置清單。

5.6 核心 patch 不能用 git diff 產生

Yocto 的 do_patch 會把舊 patch commit 進 kernel-source 的 git HEAD， git diff 只會輸出增量（實測 70 行 vs 應有 248 行）。正確做法： 對原始基線 dts 做完整 diff -u，然後乾跑重放驗證：

# 基線 + patch == 目前原始碼，位元組級一致才算數
patch -p1 --dry-run < 新patch && patch -p1 -s < 新patch && cmp 打完的檔案 目前檔案

5.7 debugfs 不跟隨符號連結

weston.ini 真身是 /etc/xdg/weston/weston.ini.weston-init（update-alternatives 管理）。 用 debugfs 驗收映像檔時要查真身檔案，否則誤報「設定缺失」。

5.8 WSL 特有

  • 從 Windows 呼叫 WSL 跑複雜指令，用腳本檔別用行內指令（引號會被 PowerShell/bash 兩層轉義打碎）
  • Git Bash 會把 /home/... 路徑重寫成 Windows 路徑，呼叫 wsl 要從 PowerShell 走

6. 與板端的關係（團隊約定）
