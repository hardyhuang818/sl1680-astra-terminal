SL1680 上跑通了完整的本地语音 AI：麦克风 → 语音识别 → 大模型对话 → 语音合成，全部在板子上，一轮对话约 5~6 秒。

并验证了 NPU 做人体检测 24ms/帧 —— 正在把它接成「人走近自动唤醒」。

一 · 完整链路与实测性能

C920麦克风 → Silero VAD → SenseVoice ASR → 事实接地/Qwen LLM → matcha TTS → Razer喇叭 切句 转文字 生成回复 合成语音

全部本地运行，一个常驻 C 程序 astra_voice 把四个模型装在一个进程里，只在启动时加载一次(~10s)，之后零加载。

环节方案实测证据
VADSilero ONNX实时切句实测
ASRSenseVoice int8RTF 0.197（4线程，5× 实时余量）实测
LLMQwen2.5-0.5B Q819.6 tok/s 生成，冷启动 3~4s实测
TTSmatcha-zh-en + vocos-16khz热合成 RTF 0.37实测
一轮对话端到端~5~6 秒（ASR 0.5 + LLM 3~4 + TTS 1）实测

进程常驻是第一优化。之前 CLI 每次合成都重载模型，白扔 11 秒；改成常驻后每轮零加载。这比任何模型级优化都重要。

交叉编译链路（可复用）：Yocto 的 gcc-cross-aarch64 + binutils-cross-aarch64 + ~/xshim 符号链接层；cmake 用 pip install（Yocto cmake-native 缺 libbz2）；llama.cpp 必须 -DGGML_OPENMP=OFF（板子无 libgomp）。

二 · 识别错误的排查与修复

用户反馈「识别错误」。我建了 6 句标准测试集，用字错率(CER) 量化每一步改动，不靠眼睛判断。

配置CER
baseline（lang=auto，Razer麦）48.6%
lang=zh51.4%
lang=zh + 前后补静音 0.2/0.235.1%
lang=zh + pad + gain5x27.0%
换 C920 麦 + 正常说话≈0%（句句全对）

根因① VAD 削掉句首清辅音 实测

Silero VAD 把「今」的 j 这类清辅音当静音切掉，SenseVoice 拿到残缺开头就糊字。

PC 对照实验：同一段「看这怎么样」→ 前面补 0.3s 静音 → 「今天天气怎么样」。只前补有效，后补没用；补零(静音)即可，不必真实音频。

根因② Razer 耳麦采得太轻 实测

Razer 的 Mic 已 100%/35 满档(+5dB)，用户「靠近清晰念」采到的仍只有 RMS 0.011~0.037（识别需 ~0.04）。

换 Logitech C920（增益 0~60/+42dB）→ 采到 RMS 0.095~0.159，响一个数量级。实时数据铁律：RMS ≥ 0.04 → 句句全对；< 0.033 → 糊。

顺带修的一个真 bug：C920 是摄像头只有麦没有喇叭，而程序原来用同一个 --dev 管采集和播放 → 直接切 C920 会让回复往没喇叭的设备播，什么都听不到。已拆成 --dev-in（C920采音）/ --dev-out（Razer出声）。

三 · LLM 幻觉 → 接地 (grounding)

用户发现回答是错的：问「现在几点」答「12点」（没读时钟瞎编）、问「天气」答「晴朗气温适宜」（没联网瞎编）。根因是回复逻辑顺序反了 —— LLM 总能吐出文字，导致报时规则永远轮不到。

修法（正是官方方案调研 md 说的 RAG/接地）：事实类问题先用真实数据回答，只有开放闲聊才交给 LLM。

问修复前（幻觉）修复后（接地）
现在几点了"现在是12点"（编）"现在是11点13分"（读系统时钟）✅
今天星期几—"今天是星期六"（真实日期）✅
今天天气怎么样"晴朗，气温适宜"（编）"没有联网，查不到实时天气"（诚实）✅
你是谁 / 讲笑话—走 LLM 闲聊 ✅

加了 --test-reply "文本" 模式，可离线自测回复逻辑不启动音频 —— 上面结果就是这么验证的。

四 · 视觉唤醒（进行中）

目标：人走近 → 摄像头检测 → 自动唤醒语音助手。比喊唤醒词体验好，也真正用上 NPU。

步骤结果证据
板上视觉栈people 人体检测模型 + synap_cli_od + NPU + GStreamer synapinfer 插件已核实
C920 出图抓到清晰画面（YUYV/MJPG, /dev/video8）实测
NPU 人体检测23.96ms/帧，person 置信 0.94实测
连续检测节奏常驻管道 ~0.4s/帧(~2fps)，够「人走近」用实测
阈值标定用框高%↔距离 定「够近该唤醒」待用户走位标定
触发集成检测到有人靠近且持续 → 触发 Astra 欢迎语待实测

这印证了整个 case 的核心判断：NPU 对视觉真强（人体检测 24ms），对语音帮不上忙（int8 量化在 A73 上还慢）。现在把 NPU 用在了它真正擅长的地方。

一个性能坑：spawn-per-frame（每帧重启 gst-launch）要 2.3s/帧（摄像头冷启动）。改成常驻管道持续出帧到文件、检测循环复用 synap_cli_od，降到 0.4s/帧，且不用写 C。

五 · 方法论：这一段我犯的错与纠正

这一段的价值不只在结果，也在排查纪律。我犯了不少错，但每个都用实测纠正了 —— 记下来避免重蹈。

我的错误假设实测纠正
"A73 无 dotprod ⇒ int8 量化都是负优化"过度泛化。VITS int8 慢 1.9×，但 SenseVoice int8 快 1.45×、llama Q4 比 Q8 还慢。逐模型实测
"RMS 归一化能救糊字"A/B 证伪：SenseVoice 前端带 CMVN 对电平不敏感，三档归一化结果完全一样
"开 Razer 的 Auto Gain Control 能提麦克风"它是播放控件，对麦克风无用
"xiaozhi 有神奇的音频前端要抄"源码级核实：py-xiaozhi 的 WebRTC APM 是死代码，0 次调用。能抄的只有 lang=zh + 别削波
构建脚本打印"✅编译成功"它靠"文件是否存在"判断，旧文件冒充成功。改成看编译退出码
采集播放用同一 --devC920 无喇叭，回复播不出 → 拆 --dev-in/--dev-out

核心纪律：先拿地面真相，再建理论。之前排查麦克风时，我为一个不存在的故障连续编了六个假设（低通/削波/混叠/端点/声道抵消/数字伪影），全错 —— 根因只是用户说的是生造词「astra」。

教训贯穿这一段：任何「只有一个来源能证明」的结论，都要用独立方法交叉验证；改 ASR 参数必须用内容已知的固定录音 + CER 数字比较，不靠眼睛/耳朵判断。
