Astra SL1680 构建环境与命令手册

日期：2026-08-01　适用：Synaptics Astra SL1680（Dolphin RDK）
SDK 版本：scarthgap_6.12_v2.3.0（Yocto 5.0 scarthgap / kernel 6.12.62）
受众：需要搭建同款构建环境的同事。本文所有数据来自实际在跑的构建机，不是抄官方文档。

核心原则：不 fork 官方 SDK。 上游钉死在 tag，我们的全部修改装在两个自有 Yocto 层里 （内核改动以 bbappend + patch 形式打在官方 linux-syna 上）。官方升级时只需换 tag 重新验证。

1. 主机要求（实测配置）

项 本机实际 最低建议
系统 Ubuntu 22.04.5 LTS（WSL2） Ubuntu 20.04/22.04，物理机或 WSL2 都行
CPU 24 核 ≥8 核（核越多全量构建越快）
内存 47 GB ≥16 GB（链接 chromium/qt 时吃内存）
磁盘 1 TB（已用 357 GB，其中 tmp/ 占 159 GB） ≥500 GB 空闲，SSD
Python 3.10.12 ≥3.8
git 2.34.1 ≥2.28

WSL2 用户注意：把 SDK 放在 WSL 原生文件系统（/home/...），不要放 /mnt/c —— 跨文件系统 IO 会把构建拖慢一个数量级。本机 WSL 虚拟盘单独挂了 1TB（/dev/sdd）。

2. 获取源码（四步，幂等）

# 1) 官方 SDK —— 版本必须钉死，勿用 master
git clone --branch scarthgap_6.12_v2.3.0 https://github.com/synaptics-astra/sdk ~/sdk
cd ~/sdk
# SDK 自带 poky/meta-synaptics 等子层；若为 submodule 形式:
git submodule update --init --recursive 2>/dev/null || true

# 2) 我们的仓库（含 meta-dlsdk / meta-tcm2-touch 两个层 + 全部文档）
git clone git@github.com:hardyhuang818/sl1680-astra-terminal.git ~/sl1680-astra-terminal

# 3) 接层（脚本幂等，重复跑无害；做两件事：symlink 层目录 + 写 bblayers.conf）
~/sl1680-astra-terminal/tools/setup_sdk.sh ~/sdk

# 4) 验证层都接上了
cd ~/sdk && source poky/oe-init-build-env build-sl1680
bitbake-layers show-layers | grep -E "dlsdk|tcm2"

3. 构建命令全集

每个新终端都要先进环境（bitbake 只在 source 之后可用）：

cd ~/sdk && source poky/oe-init-build-env build-sl1680

3.1 全量镜像（首次约 3~6 小时，视机器）

bitbake astra-media

产物在 tmp/deploy/images/sl1680/：

文件 用途
SYNAIMG/ 完整烧录包（约 2.5GB），配官方 USB 烧录工具
astra-media-sl1680.rootfs.ext4 rootfs 单独镜像
linux_bootimgs.subimg boot 包（kernel + DTB + initramfs），可单独 dd
Image-sl1680.bin / *.dtb 裸 kernel / 设备树

3.2 内核快速迭代（日常最常用，全程 约 75 秒）

改了 dolphin-rdk.dts 或内核源码之后：

bitbake linux-syna -C compile        # 大写 C：强制从 compile 重跑（含 dts 重编）
bitbake linux-syna -c deploy -f      # 强制重新部署产物

⚠️ 直接改的是 tmp/work-shared/sl1680/kernel-source/ 下的源码 —— 这个目录是易失的，cleanall 就没。改完必须回灌成 patch 放进 meta-dlsdk/recipes-kernel/linux/files/（怎么正确生成 patch 见 §5.6）。

改完后必须字节级验证 DTB（构建成功 ≠ 改动生效）：

python3 - <<'EOF'
b = open("/home/astra/sdk/build-sl1680/tmp/deploy/images/sl1680/dolphin-rdk.dtb","rb").read()
print("我的节点在吗:", b"synaptics,tcm-i2c" in b)
EOF

3.3 单包构建（改了某个 recipe 之后）

bitbake astra-voice                  # 语音主程序
bitbake sherpa-onnx                  # 本地 ASR/TTS 运行时
bitbake dl-face                      # DL7400 对话界面
bitbake synaptics-tcm2               # 触摸驱动内核模块(meta-tcm2-touch)

3.4 清理（由轻到重）

bitbake <recipe> -c clean            # 清 work 目录，保留 sstate
bitbake <recipe> -c cleansstate      # 连 sstate 一起清（强制真重编）
bitbake <recipe> -c cleanall         # 再连 downloads 一起清（会重新下载！慎用）

验证"补丁能否从零应用"用 cleansstate + 重编即可，不要动不动 cleanall。

3.5 排查与检查

bitbake <recipe> -e | grep ^SRC_URI=          # 看变量展开后的实际值
bitbake <recipe> -c devshell                  # 进 recipe 的构建环境 shell
bitbake-layers show-recipes "*tcm*"           # recipe 在哪个层
bitbake-layers show-appends linux-syna        # 谁 append 了它
oe-pkgdata-util find-path "*/astra_voice"     # 文件属于哪个包

构建日志位置：tmp/work/<arch>/<recipe>/<ver>/temp/log.do_<task>

4. 烧录

4.1 全量烧录（USB 工具，第一次/大版本用）

Windows 侧用官方 usb-tool-astra-update（板子进 USB 烧录模式）， 把 SYNAIMG/ 整目录喂给它。约 2.5GB，10 分钟内。

4.2 只刷 boot（内核/DTS 迭代用，30 秒）

板子跑着的时候直接 dd（A/B 双槽都刷）+ sha256 回读校验：

scp tmp/deploy/images/sl1680/linux_bootimgs.subimg root@192.168.5.126:/tmp/
ssh root@192.168.5.126 'sh -s' <<'EOF'
IMG=/tmp/linux_bootimgs.subimg
SZ=$(wc -c < $IMG)
dd if=$IMG of=/dev/mmcblk0p8 bs=1M 2>/dev/null
dd if=$IMG of=/dev/mmcblk0p9 bs=1M 2>/dev/null
sync
python3 -c "
import hashlib
exp = hashlib.sha256(open('$IMG','rb').read()).hexdigest()
for d in ('/dev/mmcblk0p8','/dev/mmcblk0p9'):
    got = hashlib.sha256(open(d,'rb').read($SZ)).hexdigest()
    print(d, 'OK' if got==exp else 'MISMATCH!')
"
EOF

然后断电重上（见 §5.1，这块板软复位不可靠）。

4.3 烧完镜像后还差两样

缺什么 怎么补
约 2GB 语音模型（不进镜像） 单独灌到板子 /home/voice/，清单见 meta-dlsdk/recipes-ai/astra-voice/files/README_models.md

5. 踩过的坑（每条都真踩过，按血泪值排序）

5.1 这块板软复位不可靠

reboot -f、systemctl reboot -ff、sysrq 全部无效。每次刷完 boot 都按"需要人工断电重上"来安排， 改动尽量攒成一次重启。

5.2 bbappend 文件名的版本通配规则（两边坑正好相反）

  • linux-syna 配方带版本号（6.12.62）→ append 必须写 linux-syna_%.bbappend（带 _%）
  • tzdata 配方不带版本号 → append 必须写 tzdata.bbappend（不带 _%） 写反的症状都是 No recipes available for ...，bitbake 不会告诉你是文件名的事。

5.3 cmake FetchContent 被 Yocto 硬关（症状像断网）

cmake.bbclass 默认 FETCHCONTENT_FULLY_DISCONNECTED=ON，第三方包在 do_configure 阶段 下载失败，报错看起来像网络问题——其实根本没联网。解法：全部第三方包写进 SRC_URI （带 sha256）+ do_configure:prepend 拷到源码树命中 possible_file_locations。 参照 meta-dlsdk/recipes-ai/sherpa-onnx/sherpa-onnx_1.13.4.bb（14 个包的完整做法）。

5.4 无 SOVERSION 的 .so 会被打进 -dev 包

构建全绿、包也出了，烧到板子上就是没有那个 .so ——它被分进了 -dev 包。 症状离构建极远，极难倒查。解法见 sherpa-onnx recipe 里的 SOLIBS/FILES 处理。

5.5 镜像集成四坑（构建成功 ≠ 功能完整）

① 两个包装同一个文件 → do_rootfs 冲突；② 两个服务抢同一设备（DLSDK 单进程独占）； ③ 包装进去了但服务没 enable（SYSTEMD_AUTO_ENABLE 只在 recipe 里生效， SYSTEMD_AUTO_ENABLE:pn-X 写在 conf 里不生效）；④ 验收必须 debugfs 直读产物 ext4， 别信构建清单。

5.6 内核补丁不能用 git diff 生成

Yocto 的 do_patch 会把旧补丁 commit 进 kernel-source 的 git HEAD， git diff 只会输出增量（实测 70 行 vs 应有 248 行）。正确做法： 对原始基线 dts 做完整 diff -u，然后干跑重放验证：

# 基线 + 补丁 == 当前源码，字节级一致才算数
patch -p1 --dry-run < 新补丁 && patch -p1 -s < 新补丁 && cmp 打完的文件 当前文件

5.7 debugfs 不跟符号链接

weston.ini 真身是 /etc/xdg/weston/weston.ini.weston-init（update-alternatives 管理）。 用 debugfs 验收镜像时查真身文件，否则误报"配置缺失"。

5.8 WSL 特有

  • 从 Windows 调 WSL 跑复杂命令，用脚本文件别用内联命令（引号会被 PowerShell/bash 两层转义打碎）
  • Git Bash 会把 /home/... 路径重写成 Windows 路径，调 wsl 要从 PowerShell 走
