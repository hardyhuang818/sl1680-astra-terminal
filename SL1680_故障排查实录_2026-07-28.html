1 · 麦克风完全失聪

现象：语音助手不响应，systemd 每 3 秒重拉，每次白烧 12.5 秒加载模型。

排查：arecord 直接录音也失败 → 不是应用问题。dmesg 实锤：

usb 1-1.4: 3:1: usb_set_interface failed (-71)   ← 从开机 53 秒起反复出现
usb 1-1.4: can't set config #1, error -71        ← 最终整个设备配置失败

-71 = EPROTO，USB 协议级错误。视频接口还活着，只有音频接口死了。

尝试过且无效：unbind/bind、authorized 强制重配置、端口级断电。

教训：USB EPROTO 级故障，kernel 的所有软复位手段都无效——判据是 dmesg 里的 -71，见到就直接拔插。另：C920 的音频是等时端点，总线紧张时最先饿死（它从开机 53 秒就在报错，unbind 只是把它推下悬崖）。

2 · 语音识别准确率骤降

排查：分析板上存档的语音段 /home/voice/segs/*.wav：

seg_004.wav  RMS=16932  peak=32767  削顶 2717 个采样点  ★
seg_005.wav  RMS=14390  peak=32767  削顶 2115 个采样点  ★
seg_006.wav  RMS=15546  peak=32767  削顶 3048 个采样点  ★

根因：麦克风增益 48/60 = +38dB，近距离说话打爆 16bit 满量程。削顶波形破坏高频信息，对声学模型是毁灭性的——典型表现就是吞字（"打开"→"开"）。

教训：ASR 变差先看波形，不要先怀疑模型。存档语音段（--save-dir）这个设计救了命，值得一直开着。

4 · 音量指令无效但回复"已调到最大" ⭐

排查：读 try_volume() 代码：

m = re.search(r"(\d+)", text)     # ← 只认阿拉伯数字

ASR 输出的是「音量调到百分之百」——全是汉字，没有一个阿拉伯数字。匹配失败 → 返回 None → 静默落到云端 LLM → LLM 张口就来"已经调到最大了"，什么都没做。

修复后实测：

[你 ] 音量调到百分之百。
[机器] 好的，音量调到100%。      ← 真执行了
教训（最阴险的一类）：本地规则没命中时静默回落云端，而云端 LLM 会一本正经地假装执行。系统日志一切正常，用户却发现没生效。这和"echo 已装其实没装""脚本无条件 exit 0"是同一种病：报告与事实不符。

6 · 新换的 4K 屏不亮

排查：dl_edid 读 EDID（DLSDK 单进程独占，须先停 dl-face）：

显示器名: Mi Monitor
首选模式: 3840x2160 @160Hz     ← 教科书级复现我们记录过的陷阱
支持模式: 26 个（含 @60Hz）

但 dl_face 日志显示它正确钳到了 60Hz。真正的问题是：

[dl_face] 热插拔回调注册: 失败 (status=2, handle=NULL)

根因：DLSDK 三缺陷之一——热插拔回调恒失败 + EDID/显示器列表全是缓存。dl_face 枚举一次就再没更新，换屏它根本不知道。

修复：重启 dl-face 重新枚举，两块屏立刻按 @60Hz 点亮（语音"重新检测屏幕"同效）。

7 · 天气查不到（第一层：DNS）

nslookup open.bigmodel.cn  →  198.18.26.109

198.18.0.0/15 是 RFC 2544 保留的基准测试网段，不是真实公网 IP——这是代理软件（Surge/Clash 类）的 "Fake IP" 特征。板子 DNS 是 198.18.0.2（家庭路由下发），但板子不走代理，于是解析到不可路由的假地址，所有云端 API 超时。

教训：板子换网络环境后先 nslookup。看到 198.18.x.x 就是这个坑。这类故障症状是"超时"，极易误判成 API key 失效或服务挂了。

8 · 天气仍查不到——真根因 ⭐⭐⭐

DNS 修好后，手动跑脚本成功（1-2 秒返回真实天气），服务里依然回"我现在没有联网"。

排查绕了六轮，因为每一层都在说谎

轮次假设结果
1网络不通ping 正常
2DNS 假 IP真问题，修了，但不是主因
3搜索 API 失败我的测试没带环境变量——测试本身有缺陷
4子进程超时猜的，实测只要 3 秒，不成立
5strings 搜不到那句话strings 默认只认 ASCII，中文根本搜不出来
6加调用日志日志文件为空 = astra_llm.py 根本没被调用

破局的两个动作

① 给 astra_llm.py 加调用日志（astra_voice 调它时写死 2>/dev/null，把诊断信息全扔了）：

13:11:44  IN      --stream 今天天气怎么样？
13:11:45  OUT-WX  广州现在雷阵雨，28度，体感34度，湿度88%……

日志为空就是铁证——不是调用失败，是压根没调用。

② 用 grep -a 而不是 strings 搜二进制：

$ grep -aoE "我现在没有联网[^\"]{0,30}" /usr/bin/astra_voice
我现在没有联网，查不到实时天气，抱歉。      ← ★ 内置规则，实锤

真根因

// astra_voice.c 的 factual_reply()
// 天气 —— 无数据源，诚实说不知道，绝不编
if (strstr(heard, "天气") || strstr(heard, "气温") || ...) {
    snprintf(out, cap, "我现在没有联网，查不到实时天气，抱歉。");
    return 1;      // ← 直接返回，cloud_reply 永远轮不到
}

// 调用顺序
if (factual_reply(...)) return;    // ① 天气在这里就被截了
if (cloud_reply(...)) return;      // ② 联网能力在这里，永远执行不到
⭐ 最贵的教训

这条规则写的时候是完全正确的——当时确实没有天气数据源，写它就是为了防止模型编造"晴朗气温适宜"这种幻觉。

但能力补齐之后没人回来删它。于是当年的诚实变成了今天的谎言，而且遮蔽得毫无痕迹：astra_llm.py 连调用都不会被调到，日志、错误码、返回值全都正常。

规矩：实现"没有能力时的诚实兜底"时，就要同时在代码里留下"能力补齐后必须删除此处"的标记。

顺带发现的部署坑

板上原 astra_voice 是 34MB 静态链接老产物，recipe 现在产出 67KB 动态链接版——板子 rootfs 里根本没有 sherpa 的 .so（旧镜像早于 sherpa recipe）。处理：装到 /usr/lib/sherpa + ld.so.conf.d 注册 + service 加 LD_LIBRARY_PATH 三重保险。新镜像自带 sherpa-onnx 包，无此问题。

9 · 天气回答含糊 → 接入 Open-Meteo

根因：web_search(text) 把用户原话直接当搜索词，"今天天气怎么样"里没有城市，抓回来的是随机某地新闻稿，模型只能照抄成"我市"。

修复：① 城市定位（内置 30 城，用户说了就用他说的）；② 换掉整条数据链路：

旧：搜索 + LLM 总结新：Open-Meteo
耗时5-7 秒（超时被判定云端失败）1-2 秒
数据网页新闻稿，可能几天前官方气象，实时
编造风险模型从行文里抠数字零——结构化 JSON 套模板
成本搜索 ¥0.01 + LLM token免费，不需要 API key
能力只能"今天怎么样"今天/明天、体感、湿度、降雨概率、自动提醒带伞

实测：

今天天气怎么样 → 广州现在雷阵雨，28度，体感34度，湿度88%，今天25到30度，降雨概率100%，记得带伞。[1秒]
深圳今天天气   → 深圳现在雷阵雨，28度，体感34度，湿度81%，今天25到30度，降雨概率86%，记得带伞。
明天天气如何   → 广州明天雷阵雨伴冰雹，气温25到30度，降雨概率100%，记得带伞。
北京冷不冷     → 北京现在小雨，34度，体感39度，湿度52%，今天26到35度，降雨概率41%，记得带伞。

贯穿全天的三条元教训

① 系统会说谎，而且是"正常地"说谎

今天有 4 个 bug 属于"报告与事实不符"：云端 LLM 假装执行音量指令（#4）；astra_setvol.sh 无条件 exit 0（#5）；内置规则说"没有联网"其实网络好好的（#8）；我自己的测试没带环境变量却当成"API 失败"的证据（#8 第 3 轮）。

这类 bug 最贵，因为日志、返回码、监控全是绿的。唯一的破法是拿到执行现场——加调用日志、回读核对、字节级校验。

② 诊断信息不能扔

astra_voice 调 LLM 时写死 2>/dev/null，把 stderr 全丢了。查天气时 [search] failed 这种关键线索完全看不见，只能一层层手工复现，多花至少一小时。已给 astra_llm.py 加常驻调用日志。

③ 工具本身也会骗你

strings 默认只提取 ASCII 字符串，中文一个都搜不到。我因此得出"二进制里没有这句话，所以是模型生成的"这个错误结论，导致后面几轮方向跑偏。正确姿势：搜二进制里的中文用 grep -a。
